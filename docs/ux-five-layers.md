# 記帳の画面は「確認して確定する」流れを中心に作る（UXの5階層）

Phase 1の画面を作る前に、戦略から表層までを一度通した記録です。通した結果、設計が5か所変わりました。まだ画面はなく、ここにあるのは決定の記録です。

## 戦略: 月の記帳を、手を止めずに終わらせる

使い手は、月に50〜200件の取引がある青色申告の個人事業主です。目的は、月の記帳を手を止めずに終えること。マウスに持ち替える一回一回が、記帳を面倒にしている最大の原因だと仮定しています（作者の実感で、調べてはいません）。成功の基準は、100件を取り込んでから確定するまで、キーボードだけで5分以内。この数字も仮説です。最初に、作者自身の入力で測ります。

## 要件: 5つのユーザーストーリー

- 私は、銀行のCSVを置くだけで、明細が「未確認」の列に並んでほしい。同じ明細が二重に入るのは困る。
- 私は、1件ずつ科目を直しながらEnterで次へ進み、最後にまとめて確定したい。
- 私は、確定した後に間違いに気づいたら、理由を書いて訂正したい。元の記録は残っていてほしい。
- 私は、月の終わりに、残高と消費税の見込みを見たい。
- 私は、税理士に渡す前に、弥生形式で書き出したい。

## 構造: 画面は4つ、下書きと確定は別の場所

画面は「取込」「確認」「月次」「書き出し」の4つです。確認の画面には、未確認の列と確定済みの列があります。未確認は自由に直せますが、確定済みは訂正の手続きでしか変わりません。この違いが、画面全体の構造を決めます。

## 骨格: 表1枚、フォーカスはキーボードで動かす

確認の画面は表1枚です。左に日付・金額・摘要、右に科目・税区分・メモを置きます。行の中はTab、行の移動は矢印。Enterで確定候補に入れ、Shift+Enterで確定します。

ここで一番こだわるのは、日本語入力の変換中のEnterです。変換を決めるためのEnterが、そのまま仕訳の確定として働いてはいけません。画面が「いま変換中か」を知っていることを、受け入れ条件にします。

## 表層: 数字は右寄せ、色だけに頼らない

金額は右寄せの等幅数字。貸借は色と文字の両方で示します。明暗はOSに従い、フォントは端末標準です。

## 通したことで変わった5つの決定

1. 下書きを台帳の連鎖の外に置き、確定した時だけ追記する。最初の設計案では、下書きから確定への移行が更新になり、成り立たなかった。
2. 成功の基準を、相対的な「クラウド会計比で50%短縮」から、絶対値の「100件を5分以内」に変えた。
3. 取込の重複判定に、「同じ日・同じ金額・同じ摘要の取引が本当に2件ある」場合を加えた。最初の案の指紋（日付+金額+摘要+口座）では、2件目が重複として捨てられる。
4. 「変換中のEnterは確定にしない」を、画面の受け入れ条件に加えた。日本語入力のある画面で、キーボードだけの操作を作るときの定番の不具合を、先に条件にした。
5. 月次の画面には、未確認の件数を常に併記する。未確認の明細が残っている間は、残高も消費税の見込みも変わりうるためだ。
