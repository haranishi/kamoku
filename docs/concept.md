# kamokuは「手元に控えを持つ帳簿」であり、クラウド会計の代わりではない

kamokuが狙うのは、青色申告の個人事業主が自分のパソコンの中だけで複式簿記をつけ、必要なときに弥生形式で税理士へ渡せる状態です。クラウド会計と張り合うのではなく、その横に置く手元の帳簿として始めます。この文書は、そう決めた理由と、まだ決めていないことを書きます。

## 出発点は3つの仮説で、利用者調査はまだない

作者は個人事業主で、自分の帳簿はクラウド会計でつけています。そこから立てた仮説が3つあります。いずれも作者の実感と推測で、他の人に確かめてはいません。

第一に、契約の状況に左右されず、過去の帳簿を読める形で手元に持ちたい人がいる。第二に、月に50〜200件の取引を、マウスに持ち替えずに確認して確定したい人がいる。第三に、記帳を手伝う税理士は、弥生形式のCSVなら受け取れることが多い。三つ目は、freeeが弥生会計に取り込める形式の出力を用意している（freeeのヘルプで確認）ことからの推測で、税理士への聞き取りはしていません。

仮説の検証は、Phase 4で作者自身の2026年分を並行して入力し、クラウド会計の月末残高と1円単位で突き合わせるところから始めます。突き合わせに使うのは、作者が自分のデータを公式の書き出し機能で出したファイルだけです（理由は[権利の確認記録](legal/rights-check.md)）。

## 成功の基準は、絶対値で決めて測る

「SaaSより速い」という相対的な言い方はしません。基準は次の3つで、どれも目標であり、まだ実測していません。

| 基準 | 目標 | 測る時期 |
|---|---|---|
| 100件の取込から確定まで（キーボードのみ） | 5分以内 | Phase 1 |
| 画面操作の応答（一覧のスクロール・検索・月次の再計算） | 50ミリ秒以内 | Phase 1 |
| 仕訳の貸借一致 | 仕訳の生成APIが貸借不一致を必ず拒否する（試験あり） | Phase 0で達成 |

## できないこと、しないこと

銀行口座の自動連携はしません。クラウド会計は連携で明細を自動で取り込みますが、kamokuはCSVを置いてもらうだけです。法的な位置づけが個別判断になる領域で、保守者が1人で責任を持てないためです（[設計](architecture.md)）。申告書の作成とe-Taxの送信も、v1では作りません。

電子帳簿保存法への適合も、保証できません。設計では、訂正の履歴を残す、日付・金額・取引先で検索できる、という要件に配慮します。しかし認証は取っておらず、適合するかどうかは利用者の運用で決まります。[規約まわりの整理](legal/regulation-notes.md)に、どこまで言えるかを書きました。

## いちばん大きな危険は、税のルールを1人で追い続けられないこと

この危険は、すでに現実になっています。令和8年度の税制改正で、インボイスの経過措置は「80%のあと50%」から「80%、70%、50%、30%」の段階に変わりました。2割特例は、通常の個人事業者では2026年分で終わり、令和9・10年分には個人事業者向けの3割特例ができました。計画の元になった資料は、どちらも改正前の内容でした。古い数字は、そのまま誤りになります。さらに、飲食料品の消費税率を2年間引き下げる案が出ています。国会での成立が前提の案です。

手当ては3つです。税のルールをコードに埋めず、根拠のURLと確認日をつけた表にします。表を変える変更は、国税庁の一次資料のURLがなければ受け付けません。税理士の確認が済んでいない部分は、README と crate の説明に「確認前」と書きます。それでも更新が止まった場合に備えて、計算結果の画面には、使った表の「最終確認日」を必ず出します。

## 未決のこと

名前は仮です。画面の技術も決めていません。作者の暫定の見立ては、日本語入力と大きな表の性能を試してから、Tauri（Web技術の画面）にするかを決める、というものです。基準と比較は[設計](architecture.md)にあります。
