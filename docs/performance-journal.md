# 仕訳帳の性能検証

一覧の要求ごとに、全イベントから履歴の表を作り直して全件を並べ替えていました。
台帳に登録順の参照を保ち、条件に合う全件の件数と合計を確かめた後、必要な
ページだけを選んで整列します。保存形式とハッシュの計算は変えません。

## 再現する方法

```sh
cargo run --release --locked -p kamoku-app --example bench_journal -- \
  --entries 100000 --revisions 0 --samples 10 --output /tmp/journal.json
cargo run --release --locked -p kamoku-app --example bench_journal -- \
  --entries 10000 --revisions 5 --samples 10 --output /tmp/journal-revised.json
```

一時DBへ500件ずつ合成仕訳を登録し、本物のHTTPサーバーへ要求します。
`--revisions 5` は各10番目を5回訂正し、各20番目を取り消します。
1万仕訳なら15,500イベント、うち有効9,500件、取消500件です。
DB作成・起動・参照値の作成・結果の検証は測定時間から外します。

先頭50件、末尾50件、検索0件と1件、期間、取消済みの6条件を測ります。
生成した入力から独立して全件を並べ替えた参照値と、応答のJSON全体を毎回
照合します。番号・版・履歴の時刻・金額・明細・metaも比較し、HTTP 200だけでは
成功にしません。

各条件はウォームアップ1回と測定10回です。生の時間、中央値、nearest-rankの
p95、件数、合計、実行ファイルのSHA-256とビルド条件をJSONに保存します。
要求は新しいTCP接続の開始から本文の受信完了までで、JSONの解析を含みません。
サーバーとOSのキャッシュは温まった状態です。

## CIで変更前後を比べる

`journal-performance` は同じrunner・Rust・release設定でbase/headをビルドします。
測定プログラムの2ファイルをbaseへも写し、同じ測定処理をそれぞれの実装に
リンクします。ビルド先は分離し、古い成果物を共有しません。

1万件・10万件の訂正なしと、1万件の訂正ありをそれぞれ測ります。結果、ソースの
SHA、Rust情報を14日間保存します。認証情報・DB・サーバーログは保存しません。
正式な結果とrunのURLは、PRの検証欄に記録します。

## 未確認の範囲

単一の合成データとCI環境の比較です。入力の分布、ディスク、OS、同時操作により
実測は変わります。検索文字列の索引や、帳票の集計結果のキャッシュは加えて
いません。Rust製画面の初回表示と入力から描画までの時間は別に検査します。
