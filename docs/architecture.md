# 設計の判断: 追記だけの台帳、日付つきの税表、通信しない

コードを読めば分かることは書きません。ここに残すのは、なぜその形にしたか、何を捨てたか、どこに限界があるかです。最初の設計案（Driveの資料。AIの生成物と見られる）から変えた点は、「変えた点」と明記します。

## 金額は整数の円で持つ

金額は `i64` の円（`Yen`）で持ちます。消費税の端数処理は、1円未満を切捨て・四捨五入・切上げのどれにするかで、計算の場面ごとに使える方法が決まっています（適格請求書の税額は事業者が方法を選べ、経過措置の仕入税額は切捨てか四捨五入）。どれも整数の割り算で再現できます。小数型の依存（`rust_decimal`）は入れませんでした。SQLiteには10進数の型がなく、保存のたびに文字列との変換が要るため、変換の誤りが入り込む場所が増えるからです。`f64` は使いません。

## 訂正は追記し、過去の記録は書き換えない

仕訳の登録・訂正・取消は、どれも新しいイベントとして台帳の末尾に足し、SHA-256でつなぎます。訂正は理由が必須で、元の版は残ります。

**変えた点**: 最初の案では、訂正のときに過去のブロックの状態を書き換えてハッシュを再計算していました。これだと後ろに続くブロックの連鎖が壊れます。しかも、保存側で更新を禁じる仕組みを置く案と矛盾します。kamokuは、過去のイベントに一切触りません。現在の状態は、イベントの列から計算します。ハッシュの対象には、形が保証されないDebug出力を使わず、バイト列の符号化を文書とゴールデン値の試験で固定しました（`crates/kamoku-ledger/src/encoding.rs`）。

限界は2つあります。連鎖は改ざんを**検知**するだけで、防ぎません。また、末尾のイベントの削除や、全体を計算し直して作り替えることは、連鎖だけでは見つかりません。月末に `head_hash` を紙・メール・Gitのどこかへ控えておくと、後から比べられます。

この仕組みで電子帳簿保存法の要件を満たすとは言いません。法が求めるのは「訂正・削除の履歴が残る、または訂正・削除ができないシステム」などの措置で、該当するかは運用を含めて判断されます。

## 下書きは連鎖の外に置く（Phase 1で実装）

CSVから取り込んだ明細は「下書き」の表に入り、自由に直せます。確定した時だけ、台帳へイベントとして追記します。**変えた点**: 最初の案は、下書きも確定済みも同じ表に入れ、更新を禁止する仕組みも付けていました。それでは下書きから確定への移行が更新になり、成り立ちません。

## 税のルールは、根拠つきの日付表にする

税率や経過措置の割合は、コードに書き込まず `kamoku-jp-tax` の表に置きます。各行に、適用期間、割合、国税庁の資料のURL、確認日を付けます。令和8年度の改正で、免税事業者等からの仕入れの経過措置は「80%、70%、50%、30%」の段階になりました（国税庁のQ&A 問113-3）。最初の案は80%と50%を列挙型に書き込んでいたので、この改正で誤りになります。改正があれば表に行を足し、過去の日付の結果は変えません。税率そのものも、飲食料品を令和9年4月から2年間1%にする案があるため、日付つきの表にするのが次の課題です。いまの実装は、標準10%と軽減8%を固定で持っています。

## 通信しない。外へ出すのは、利用者が選んだときだけ

既定では外部へ何も送りません。AIによる仕訳の提案を入れる場合は、送る項目と送り先を画面に出し、利用者が選んだときにだけ送ります。モデルはアプリに同梱しません。

## やらないと決めたこと

| やらないこと | 理由 | 見直す条件 |
|---|---|---|
| 銀行・カードの自動取得 | 銀行法の電子決済等代行業に当たりうる。口座情報を銀行から取得して利用者に伝える行為は一般論として該当すると金融庁が示しており、該当性は個別に判断される。保守者1人では責任を持てない | 弁護士か金融庁から、該当しないという見解が得られたとき |
| マネーフォワード形式の書き出し | 同社の規約が、契約者による競合サービスの開発・改良を禁じている。契約者として実機で確かめることができない | 規約の確認と法的な見解が得られたとき |
| 申告書の作成とe-Taxの送信 | 保守の負担が大きい。v1の範囲外 | 税理士の協力者が現れたとき |
| 重複取込の自動判定の確定 | 同じ日・同じ金額・同じ摘要の取引が本当に2件ある場合を落とさない方法が未決 | Phase 1で、合成データを使って比較する |

## 画面の技術は、試してから決める

候補はTauri（Web技術の画面）、egui、icedです。決める基準は2つで、日本語入力の変換中のEnterで確定されないこと、数万行の表のスクロールが50ミリ秒以内に収まることです。Phase 0では、どれも選びません。

## 保存はrusqliteを使う

SQLiteの操作は `rusqlite` を使い、`sqlx` は使いません。個人のパソコンで1人が使うので、非同期もコンパイル時のDB接続も要りません。`kamoku-ledger` は入出力を持たない純粋なライブラリにして、保存の層から切り離します。
