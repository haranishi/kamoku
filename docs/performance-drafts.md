# 未確認明細の性能検証

ホームと明細の確定処理は、未確認明細を500行ずつ読み直していました。
各ページで件数の集計・並べ替え・全項目の復元が走るため、件数が増えると
処理が急に遅くなります。合計金額はamount列の1回の走査、確定対象は主キーの
直接取得に変え、金額の上限と確定時の再検証を保ちます。

## 再現する方法

```sh
cargo build --release --locked -p kamoku-app --bin kamoku
python3 tools/bench-draft-queries.py --binary target/release/kamoku \
  --rows 100000 --samples 10 --timeout 5 --require-complete \
  --output /tmp/kamoku-pending-drafts.json
```

Python標準ライブラリと指定した実行ファイルだけを使います。架空の明細を
一時DBへ用意し、ホームと1行確定を別々のDB・サーバーで測ります。合計や
確定結果の内容も検査し、HTTP 200だけでは成功にしません。認証用URL・Cookie・
DB・サーバーログは結果へ含めません。

CIの `performance` は、PRのbaseとheadを同じrunner・Rust・release設定で
ビルドし、1万行と10万行を各10回測ります。JSON、ソースのSHA、Rustの情報を
14日間保存します。baseの時間切れは下限として記録し、成功した測定値からの
中央値・p95と区別します。headは全試行の完了を必須にします。

## 調査時の参考値

2026-10-15、macOS 27.0.1 arm64、既存のdebug実行ファイルでの予備調査です。
再ビルドしておらず、現在の依存lockより古い可能性があります。
この数字とreleaseの結果から改善倍率は計算しません。

| 条件 | ホームの応答 | 1行確定 |
|---|---|---|
| 未確認1万行、仕訳約1万件、各3回 | 中央値400.4ms、p95 401.8ms | 中央値373.7ms、p95 382.6ms |
| 未確認99,997行、仕訳10,036件、1回 | 20秒で時間切れ。成功値なし | 未測定 |

予備調査では、ホーム処理中のstatus応答も約355ms待たされました。
単独のstatus応答の中央値は約1.1msです。同期的な処理時間を減らす目的が
ありますが、同時利用時の改善幅は別に測る必要があります。

## 適用範囲

CIは仕訳0件、同額の未確認出金という合成条件です。帳簿の集計、保存先の
ディスク、実際の操作時間、すべてのOS・ブラウザの速さは、この比較だけでは
判断できません。Rust製UIへの移行による速さも別に測ります。
